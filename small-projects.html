Case study · Tools

Small tools, built because something bigger needed them.

None of these started as a project. Each one exists because a specific job could not be done with something already installed, and the honest version of that job turned out to be a few hundred lines rather than a new platform.

Why it exists

A monorepo of small services, each with its own Taskfile, its own image and one shared CI workflow. The rule is the same everywhere: solve the narrow problem, keep the interface small, do not grow a platform out of a script.

How it works

  • One Taskfile per app, included from the root, so a newcomer runs the same three commands for every tool.
  • One image per app, built by the same workflow with a tag derived from the run, published to a registry path per app.
  • Small surfaces. media-svc exposes four routes: three operations and a health check. Nothing else, no admin API, no state.

Lessons learned

The monorepo is the right shape until one app grows its own release cadence, then it is a drag on everything else. The two projects that left were both the ones with a database.

A shared CI workflow is worth it from app two, and painful to retrofit from app five.

What I would do differently:

  • Write the one-line purpose of each app in its README at creation. Half of these had none, which is why this page needed reading code to describe them.
  • Keep the health endpoint from the first commit; it is the cheapest thing to add and the first thing every consumer asks for.
  • Retire loudly. A dead folder left in place reads as "unfinished" rather than "replaced".
