Case study · Infrastructure

Two machines, one seam, nothing applied by hand.

Second-hand hardware, one x86 box and one ARM board, carrying a cluster that runs like production. Ansible provisions the machines. Flux delivers everything above them from Git, and the two never share a tool.

Why it exists

homelab-core is the machine layer: OS baseline, hardening, firewall rules, K3s install, join and upgrade, node labels. One Taskfile entry point per operation, so rebuilding a node is a command, not a test of memory. It stays private because it encodes host addresses and the shape of the network, and none of that is needed to read the work above it.

homelab-gitops is the deployment layer. It holds what Flux reconciles: applications, routes, dashboards, alerts and scrape configs. It stays private as well, not because of what the current files contain but because the history maps the live topology one commit at a time.

homelab-projects is the application layer: small services, each with its own Taskfile, image build and CI job. It holds no hosts and no data, so it is the half that can be published as it stands. Today it is still private.

homelab_workflows is the fourth repository and not a service at all. It holds the prompts and JSON schemas that workflows fetch at run time. No build, no image, just the contracts.

Every repository also carries openspec/ for change specs and docs/ for its own notes. The tree shows the paths that define each layer, not every directory.

How it works

  • Bootstrap. One command installs SSH access, then Python and Ansible dependencies, then the K3s server. Joining an agent is a token the control plane generates, so no secret is ever copied into a repo.
  • Scheduling by architecture. Node labels keep ARM64 workloads off the x86 control plane and vice versa. Multi-arch images are the default, not an exception.
  • Reconciliation. Flux watches the cluster's Kustomization tree and applies Kustomizations; Helm releases are declarative values files. A merged PR is the only way anything changes.
  • Storage. Persistent volumes are iSCSI targets on a NAS, so a node can be rebuilt without losing data.
  • Observability. VictoriaMetrics scrapes the cluster and Alertmanager routes to a chat channel. Alert routing exists before the workload that needs it.

Lessons learned

Not the YAML. The hard part was deciding where the machine ends and what runs on it begins, then defending that line when the fast path was to SSH in and fix something.

The second hard part was storage. Once volumes live on the network, rebuilding a node is free, but the NAS becomes one dependency every workload inherits. That has to be accepted on purpose rather than discovered during the first outage.

What I would do differently:

  • Alerting and backups before the third application, not after the tenth.
  • External secrets from day one. A frozen secret store silently freezes every routing rule that depends on it.
  • Resource limits at the start. Throttling looks exactly like a slow application until you measure it.
