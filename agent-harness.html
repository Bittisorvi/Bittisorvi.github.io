Case study · Agent infrastructure

The harness, not the prompts.

A prompt is the easy part. What decides whether agents are useful is the environment around them: who may touch what, when they must stop, and what proves the work. This is that environment: one orchestrator, five specialists, a kanban board as the unit of work, and a verification ladder that starts at the first file write.

Why it exists

Unattended agents without a harness produce work nobody can verify, at a volume nobody can review. The harness exists to make autonomy cheap to grant: narrow mandates, explicit permissions, and a check that fires before the mistake is expensive.

The configuration stays private because it is bound to one machine's credentials and paths. The shape is what matters here, not the file.

How it works: profiles

Each profile is a mandate, not a model setting. The orchestrator picks the cheapest profile that can finish the task, and escalates only after a specialist has failed twice.

How it works: the verification ladder

Five rungs, cheapest first. A task takes the highest rung that can actually catch its failure mode, not the most impressive one.

What runs without a human, and what it catches
RungMechanismFailure it catches
1 · write timeshell hook runs a syntax check on every file writebroken syntax, visible to the agent in the same turn
2 · repo checksshell linting, byte-compilation, unit and end-to-end testslogic and style regressions
3 · eval cronsscheduled gates over triage and handoffs, run as cron jobsdrift across the whole fleet, not one run
4 · review gatearchitect review and merge; risky changes escalate to a humandesign and trade-off errors no machine gate sees
5 · deployedrollout status, endpoint probe, screenshot"merged" being mistaken for "works"

Rung 1 is the reason the rest is affordable: a mistake costs one turn, not one review cycle.

How it works: the gates

  • Permission by allowlist. Shell hooks are consented per command pattern. An agent cannot quietly acquire a capability it was not granted.
  • One card, one worktree, one branch. Parallel work does not collide, and a dead run leaves salvageable work on disk instead of a half-edited main.
  • Pull requests only. Nothing lands on a protected branch without passing the checks and a merge decision.
  • Merge authority is explicit. Coders never merge. The architect reviews and merges solid PRs on infrastructure repos, and hands risky or uncertain ones to a human. Credentials, alert routing and product decisions always stop at a human.

Lessons learned

Autonomy is not a dial. It is three conditions that must all hold: the work is independent, documented, and split into chunks small enough to check. Two out of three produces confident wrong work, which costs more to unwind than doing it interactively would have cost.

And the cheapest gate has to exist first. Anything fancier is decoration until the write-time check is real.

What I would do differently:

  • Roll the write-time check out to every worker profile on day one. Mine shipped for the orchestrator only; the workers that write the most code ran unchecked the longest.
  • Treat "task is parked" as a state the kernel enforces, not a note the next worker reads and respects. It does not hold.
  • Measure the fleet before adding the fifth specialist. Four would have been enough for months.
