Case study · n8n

A deal digest that remembers what it already told you.

Once a week, a list of store pages is checked for offers, grouped by category, and posted to Discord as one thread per category. Scraping is the easy part. The work is staying quiet when nothing has changed.

  • 45nodes in the flow
  • 2ways to read a store
  • 30days of deal memory
  • 1thread per category

Figure 1. One weekly pass: read each store, keep one record per product, and deliver only what the deal store has not seen.

Why it exists

Store offers change on their own schedule. Checking a handful of pages by hand every week is the kind of job that gets skipped as soon as the week gets busy, and a feed that repeats itself gets muted within a month. The flow is built around one rule: it speaks only when something changed. Everything else follows from that.

How it works

  • The sheet is the config. Each row is a store page with a category, an optional keyword filter, a minimum discount and who to notify. Adding a store is a new row, not a deploy.
  • Two ways to read a store, one record. A Shopify store exposes products.json, so prices and compare-at prices come straight from the source. Every other store goes through a scraper and a model pass that returns product lines. Both paths produce the same record, and the keyword filter, the minimum discount and the sort run once, after they merge.
  • The deal store is the memory. Each product gets a key built from the store, the name and both prices. A deal seen in the last 30 days is counted and kept out of the thread. A price change makes a new key and re-alerts on purpose.
  • Delivery is per category. One header and one thread per category, split under Discord's 2000-character limit without cutting a product line. A category with nothing new still gets a header, so a quiet week is visible rather than silent.
  • Failure stays local. A store that fails is recorded and named in the run summary while the rest of the run still delivers. If the deal store cannot be read, the run treats everything as new and says so.

Lessons learned

The cheapest source wins. products.json is faster, cheaper and more accurate than reading a page, so the model only runs where a store has no feed. Starting with the model would have been the expensive way to learn that.

Identity is a design decision. Keying a deal on the store and the name would have silenced price drops forever, because a drop keeps the same name. Including both prices makes a drop look like a new deal, which is exactly what the reader wants.

The first version paired scraped results to sheet rows by position. One Shopify row was enough to shift every later row, so products landed under the wrong category header. The fix was to pair on the normalised URL and attach row identity at construction. Position is never an identity.

What I would do differently:

  • Wire every error output on the day the node is added. A silent failure branch is a failure that waits for a quiet week.
  • Keep the graph in Git, not only in n8n's version history.
  • Test the failure path first. The happy path gets exercised every week anyway.
